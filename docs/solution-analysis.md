# 方案：memex —— agent 驱动的跨仓库「实现借鉴」知识库

> **修订版。** 原方案把「分析」做在服务端（MCP server 自己接 LLM）。本版改为：
> **分析、判断、生成、写入全部由调用 MCP 的 agent 完成**；server 只做三件事——
> 暴露接口、存取内容、强制校验，外加一个可选的 Web 展示页。
> 改动的原因与代价见第四节。未定项的最终选择（A–E 五组 21 条 + G 组 24 条）见 [`decisions.md`](decisions.md)。

---

## 一、需求拆解

原始需求：

> 填 GitHub 地址 → AI 分析整仓内容与各功能实现 → 形成知识库 → 后续 agent 实现某功能时，自动借鉴已分析项目中类似的实现。

四个环节，难度极不均匀：

| 环节 | 内容 | 难度 | 现状 |
|---|---|---|---|
| **A 理解** | 把一个仓库读懂：结构、入口、各功能怎么实现 | 中 | **已解决**，成熟项目很多 |
| **B 沉淀** | 把理解结果结构化成可检索的资产 | 中 | **部分解决**，多为文档/wiki |
| **C 召回** | 写新功能时，按「功能意图」找回旧实现 | **难** | **基本空白** |
| **D 注入** | 让 agent 在合适时机自动用上召回结果 | 中 | **基本空白** |

**关键判断：A 环节的红海不值钱，C+D 才是这个需求真正的价值所在，也是没人做好的地方。** 方案重心必须压在 C 和 D 上。

### 1.1 本次修订引入的新维度：每个环节「由谁执行」

原方案默认所有环节都在 server 内完成。修订版把执行者拆开：

| 环节 | 原方案 | 修订版 |
|---|---|---|
| A 理解 | server 的 LLM | **agent 的 LLM** |
| B 沉淀 | server 落库 | **agent 提案 → server 落库** |
| C 召回 | server 检索 | server 检索（不变） |
| D 注入 | server 暴露 MCP | server 暴露 MCP（不变） |

**这个拆分是全案的核心，因为它决定了「什么必须留在 server」。**

## 二、现状调研结论

### 2.1 生态地图（按「解决哪个环节」分类）

**只做 A（读懂仓库）——最拥挤：**

| 项目 | ★ | 做什么 |
|---|---|---|
| DeusData/codebase-memory-mcp | 44.9k | tree-sitter 162 语言 + 知识图谱，17 个 MCP 工具，Linux kernel 28M LOC 3 分钟索引 |
| oraios/serena | 29.8k | 语义检索 + 编辑，「the IDE for your agent」 |
| vitali87/code-graph-rag | 5.2k | tree-sitter + Neo4j 图谱，monorepo 导向 |
| CodeGraphContext | 4.2k | 代码索引进图数据库，`cgc mcp start` |
| cocoindex-code | 2.7k | 轻量 AST 语义代码搜索，`ccc mcp` |
| deepwiki 系列（open 18k / AIDotNet 3.6k / deepwiki-rs 3.1k / …） | — | 生成文档帮人看懂仓库 |

共同特征：**索引的是「代码」，回答的是「这个仓库里有什么」**。全是单仓视角。

**擦边做 B/C 的——极薄：**

| 项目 | ★ | 做什么 | 为什么不够 |
|---|---|---|---|
| reposwarm | 272 | 多仓架构上下文 → 生成 Architecture Hub repo | 视角是架构/依赖，不是「功能怎么实现」，无按意图召回 |
| pattern-vault | 8 | 抽可复用代码模式 → SQLite + MCP | 形态最接近，但检索是 FTS5/BM25 关键词**非语义**，无证据链 |
| h-codex | 27 | 跨仓语义代码检索 | 只是检索，无「分析沉淀」层 |
| agent-in-sync | 5 | agent 共享知识库 | 人工提交经验，非自动分析仓库 |
| Penelopa.ai | 138 | 分析 agent 会话找重复工作流 | 分析的是会话，不是仓库 |

**已排除的类别**：许可证扫描、打补丁、溯源链——不构成竞品。

补充扫描（GitHub API 检索 `codebase memory mcp` / `repo knowledge graph agent` / `cross-repo context`）未见新竞品；`Kage`（33★）、`n2n-memory`（7★）、`marm-memory`（404★）都是**会话/记忆层**，不是仓库实现层。

### 2.2 结论

> **「A 环节」有 4 万★ 的成熟方案，「C+D 环节」最好的项目只有 8★。这个需求的交叉点，GitHub 上确实是空的。**

原因：做 A 是「索引代码」，是工程问题，可验证、可规模化；做 C 是「判断什么值得借鉴」，需要**先定义知识的粒度和结构**，是产品问题，没有标准答案——所以大家绕开了。

**值得注意的是，上述所有 A 类项目都是「server 自带分析引擎」的形态。** 本方案的 agent 驱动拆分，在生态里没有先例，这既是机会也是需要验证的风险点（见第六节）。

### 2.3 你的 VibeCraft 恰好卡在这里

VibeCraft 的 Repo Library 不是空白，它已经做到 B 了：

- 完整链路：UI 表单 → API → 分析引擎 → 持久化，四层资产（正式报告 / 知识卡片 / 证据链 / 搜索索引）
- 分析引擎 `services/repo-analyzer/`（extract_cards 1244 行 / validate_report 385 行 / search 303 行）
- 混合检索：sqlite-vec + FTS5（`searchdb/vec.go` LoadExtension `sqlite3_vec_init`）
- 报告契约：4 个 H2 段落 + 5 个原理轴

**但它缺的正是 C 和 D**：

```
$ grep -rl "repolib" backend/internal/{orchestration,expert,chat,mcpgateway}/
（零结果）
```

repo-library 的检索索引，**在编排层、专家系统、对话层、MCP 网关里零引用**。报告做出来了、卡片存下来了、索引也建好了，但**没有任何代码路径能让「写功能时的 agent」去查它**。

它的规划文档 `docs/cli-pivot-and-repo-library-plan.md` 定义了 Layer 1 Ingest / Layer 2 Search / **Layer 3 Reuse**，而 Layer 3 状态是「设计草案/待落地」——**这个需求，你两年前就把路线图画对了，只差最后一段。**

## 三、这个需求的真正难点

### 难点 1：粒度——「功能」这一层是空的

| 粒度 | 问题 |
|---|---|
| 仓库级 | 一个仓几十上百个功能，召回一个仓等于没召回 |
| 文件 / chunk 级 | 太细，不成「功能」，检索到半截函数无法判断该不该借鉴 |
| **功能 / 机制级** | **这才是需求说的「某个功能」** —— 但它不是代码里现成的结构，必须被「识别」出来 |

**全案最核心的判断：必须人为定义「功能」这一中间粒度，并让分析阶段按它切分。** 现有工具全都跳过这一步（直接索引代码），所以它们在 C 环节必然失效——检索单元和用户的意图单元对不上。

这也决定了分析**必须由 LLM 做**：`tree-sitter` 能给你函数和调用图，但给不了「这是个带退避与截止时间的重试引擎」这种**功能语义**。

### 难点 2：可借鉴性 ≠ 语义相似

两个都讲「重试」的实现，一个可能是 300 行依赖注入半框架，一个是 3 行公式。语义相似度会把它们排在一起，但只有后者值得借鉴。

**必须显式建模「可复用性」维度**：卡片带 `reusable` 标记；按 kind 分级（`snippet` 直接抄 / `skeleton` 抄结构 / `mechanism` 抄思路 / `gotcha` 避坑 / `decision` 抄权衡）；检索可按 kind 过滤。

### 难点 3：跨语言匹配

同一算法的 Python 和 TypeScript 版本，**代码向量差异极大**（语法、命名、类型标注都不同）。

**可行路径：不要对「代码」做向量，要对「描述」做向量。** 让分析产出语言中立的机制描述（"指数退避，按次数翻倍再用上限截断"），对描述建索引；代码只作为附带的可抄产物。这样「Python 的重试」和「TS 的重试」在描述空间里天然接近。

这是能否满足「跨语言」要求的**分水岭设计**。

### 难点 4：信任——agent 拿到的代码必须是真的

LLM（无论是谁的）都会一本正经地编造 `src/utils.ts:42`。如果 agent 拿编造的代码去「借鉴」，比没有知识库更糟——它会以为自己在复用，实际上在幻觉。

**证据链是必需品，而且必须强制**：路径真实存在、代码从真实文件按行号重切覆盖。

### 难点 5：触发——知识库没人查就是死数据

如果依赖用户记得「去查一下知识库」，这工具 90% 的时间不会被用。

**必须暴露成 agent 可自主调用的 MCP 工具**，并在 server instructions 里明确要求「实现非平凡功能前先查」——把「记得用」变成「自动用」。

### 难点 6（本次修订新增）：分工边界——机械活必须留在 server

这是 agent 驱动架构特有的风险，也是它最大的陷阱：

**如果把「读仓库、理解仓库」整个交给 agent，agent 会烧掉自己的上下文窗口。** 分析一个 5 万行仓库，很可能把窗口填满 80%，然后它没余量做用户真正交给它的任务了。

```
原设计：build_evidence_pack() 把仓库压成几千 token 的简报 → 这是 server 的职责
agent 驱动下若省掉它：agent 自己读整仓 → 吃掉自己的 context
```

> **原则：机械活儿留在 server，判断力交给 agent。**

具体地：静态分析（数文件、找入口、抽符号、压简报）不调模型、可并行、结果确定，是纯计算——留在 server 能省 agent 的 token；而「这个功能是什么、值不值得借鉴」是判断——必须 agent 做。

还有一个效率要点：**`fetch_repo` 应返回本地克隆路径**，让 agent 用自己的 `Read`/`Grep` 工具（更快、可并行）。**不要把 MCP 当文件系统代理**，每个文件读一遍都走 MCP 是纯浪费。

## 四、路线对比与「谁来跑分析」

### 4.1 三条候选路线

| | **A. 纯 RAG** | **B. LLM 深度分析 + 结构化沉淀** | **C. 纯静态分析（图谱）** |
|---|---|---|---|
| 做法 | 仓库切块 → embedding → 相似度检索 | LLM 按契约产出报告/卡片/证据 → 语义索引召回 | tree-sitter 抽符号/调用图 → 图查询 |
| 代表 | 通用 RAG | VibeCraft 路线 | codebase-memory-mcp |
| 建库成本 | 极低 | **高**（每仓一次 LLM 全量分析） | 低（3 分钟 28M LOC） |
| 能否识别「功能」 | ✗ 做不到 | **✓ 唯一能做到的** | ✗ 只有符号和边 |
| 可借鉴性分级 | ✗ | **✓ 可显式建模** | ✗ |
| 跨语言 | 差（代码向量） | **好（描述向量）** | 中（按符号名） |
| 证据可靠性 | ✗ 会编 | 需强制校验（可做到） | **✓ 天然真实** |
| 可解释性 | 差 | **好（有报告）** | 中 |
| 增量维护 | 易 | 难（改代码要重析） | **易** |
| 适合回答 | 「哪有相似代码」 | **「这个功能该怎么实现」** | 「谁调用了谁」 |

**结论：B 是唯一能满足需求的路线**，因为只有它能产出「功能级、语言中立、带可复用性判断」的知识单元。A 和 C 都做不到难点 1。

**但 B 有两个弱点，用 A 和 C 补：**

1. **建库耗时 / 上下文消耗大** → 用 C（静态分析）做**证据包**：先静态抽出仓库骨架（入口点、模块树、符号清单），喂给分析者，比把整个仓库塞进上下文**占得少且更准**。
2. **召回不精确** → 用 A 做召回层：向量 + 关键词融合检索。

**推荐方案 = B 为主体，C 做证据采集，A 做检索层。** 对应 VibeCraft 规划的 Layer 1/2/3。

### 4.2 B 路线的两种形态（本次修订的核心）

路线选 B 之后，还有一个原方案没问的问题：**B 由谁的模型来跑？**

| | **B1. 服务端模型**（原方案） | **B2. agent 模型**（修订版） |
|---|---|---|
| 模型配置 | 需要 `LLM_CMD` / `BASE_URL` / key / fixture 四套 | **完全没有** |
| 模型数量 | 两套（agent 的 + server 的） | 一套 |
| server 端 AI 依赖 | LLM 客户端 + embedding 两套 | 只有 embedding 一套 |
| 上下文 | server 的模型看不到 agent 看到的代码 | **agent 用的是真实、最新的上下文** |
| 交互优势 | — | agent 能边看你要改的代码边分析参考仓 |
| 批量分析 | **强**（脚本一跑，20 个仓） | 弱（agent 一轮轮跑，苦力活） |
| 生态先例 | 全部 A 类项目都是这个形态 | **无先例** |

**关键洞察：B1 等于在 agent 已经有一个更好的模型、而且可能已经把目标仓库读进上下文的情况下，再养一个更弱、更没有上下文的模型。**

第四行是最别扭的地方：agent 说「我在写一个重试功能」，server 的模型根本不知道 agent 手上有哪些约束、要改哪个文件。

**结论：以 B2（agent 驱动）为主叙事，B1 作为补充的批量模式保留。** 理由见下节；B1 的代码保留，因为它解决了 B2 唯一的短板（批量）。

## 五、推荐方案：agent 驱动的 memex

### 5.1 架构

```
        ┌── 建库（agent 驱动，每仓一次）──────────────────────────┐
仓库URL → agent: fetch_repo(url)
              └→ server: clone，返回 repo_id + commit + license + 本地路径
          agent: get_evidence_pack(repo_id)
              └→ server: 静态分析 → 压缩简报（入口点/模块树/符号清单）※不调模型
          agent: 用自己的模型 + 自己的 Read/Grep 读代码，判断哪些是「功能」
              └→ 产出报告（功能 → 五原理轴 → 卡片 → 证据）
          agent: validate_report(report)
              └→ server: 纯校验，幂等，不乱写库（提交前自查，省 turn）
          agent: commit_report(session_id, report)
              └→ server: 全量校验 + 代码从真实文件重切 → 落库 ※唯一写入口
        └──────────────────────────────────────────────────────────┘

        ┌── 召回（在线，每次写功能）───────────────────────────────┐
agent → search_implementations(功能意图) → 混合检索 → 跨仓结果 + 真实代码 + 证据
        └──────────────────────────────────────────────────────────┘
```

### 5.2 分工边界（本方案的第一原则）

| 环节 | 归属 | 理由 |
|---|---|---|
| 抓取 / clone | **server** | 机械，且要统一管理缓存目录 |
| 静态证据包 | **server** | 纯计算，不调模型；留着以免吃掉 agent 上下文 |
| 按需文件切片 | **server** | 机械；但优先让 agent 直接读本地克隆 |
| **分析、判断、生成** | **agent** | 它已有更强的模型和更真实的上下文 |
| **校验** | **server**（写入路径强制） | 必须与「谁生成的」无关 |
| **落库** | **server** | 唯一写入口，事务 + 约束 |
| 召回 / 检索 | **server** | 知识库自身职责 |
| 流程引导 | **server**（会话状态机 + `next_step`） | 不能指望 agent 记得步骤 |

**只有「生成和判断」交给 agent。** 这条边界是全案能否成立的关键。

### 5.3 工具面

| 类别 | 工具 | 说明 |
|---|---|---|
| **机械** | `fetch_repo(url)` | clone；返回 `repo_id` / `commit` / `license` / **本地克隆路径** |
| | `get_evidence_pack(repo_id)` | **目录树 + 入口点 + 符号清单**；不给代码切片，agent 自己 Read；**不调模型** |
| | `read_file_slice(repo_id, path, start, end)` | 按需取真实字节（别整文件塞） |
| | `request_repo_bundle(repo_id)` | **仅远程形态需要**：server 把克隆打成 `git bundle` 单文件下发，agent 拉回本地自己 Read/Grep，换取零 MCP 文件往返（见 `tech-design.md` §4.2） |
| | `upload_repo_bundle(file)` | **仅离线/私有/内网**：反向投喂 —— 开发机 bundle 好送进 server，server 不出网也不持凭据（G22，`mcp-tools.md` T17） |
| **写入（带校验）** | `begin_analysis(repo_id)` | 开会话：返回 `session_id` + 证据包 + 契约 schema + 步骤清单 |
| | `validate_report(report)` | **纯校验、只读、幂等** —— agent 提交前自查用 |
| | `commit_report(session_id, report)` | **唯一落库口**，全量校验；失败返回全部问题 |
| **召回** | `search_implementations(query, …)` | 主入口 |
| | `get_card` / `list_patterns` / `get_report` / `list_repos` / `recall_stats` | |
| **元** | `help(topic)` | `analyze-flow` / `report-contract` / `card-kinds` / `search-usage` / `patterns`；固定 topic 集，按需取，任何 MCP 客户端都能读 |
| **破坏（默认禁用）** | `forget_analysis(analysis_id, confirm)` / `forget_repo(repo_id, confirm)` | 硬删 + 级联 + 重聚类；须显式 `confirm: true`（`decisions.md` G8，落为 `mcp-tools.md` T15/T16） |

> 逐工具的完整签名（入参/出参 JSON Schema、`annotations`、错误码）见 [`mcp-tools.md`](mcp-tools.md)；
> 报告契约（机器可读 [`report.schema.json`](report.schema.json) + 散文 [`report-contract.md`](report-contract.md)）。
> 工具总数 **17**（含 `request_repo_bundle`、`upload_repo_bundle` 与两个破坏性 `forget_*`）。
> 仅 batch 版 `analyze_repo`（G21）**尚未纳入**本版工具面。
> `resources` / `prompts` **明确不实现**（G27）。

关于 **skill**：方向对，但 skill 是**客户端私有格式**（Claude Code 的 skill 未必通用）。建议分三层，保持客户端无关：

1. `initialize.instructions` —— **一句话**触发（「实现非平凡功能前先查」）。放长了会被忽略，所以只放触发条件。
2. `help(topic)` —— 结构化流程，**任何 MCP 客户端都能读**。
3. skill —— 可选的便利层，装「怎么做好一次分析」这类长篇方法论。

### 5.4 会话状态机（替代原来的「一条命令跑 8 步」）

原来 `analyze <url>` 一条命令跑完 8 步。agent 驱动后这 8 步变成 agent 的事——**agent 一定会漏步骤**（跳过校验、只分析一半就提交）。所以要有服务端会话：

```
begin_analysis(repo_id)
    → { session_id, evidence_pack, report_schema, checklist: [...], next_step: "..." }

commit_report(session_id, report)
    → 全部问题列表（不是一次报一个）
    → { ok: false, problems: [...], next_step: "..." }
    → { ok: true, analysis_id, counts, quality: {...} }
```

**响应里带 `next_step` 提示，自导向**——服务器知道 agent 走到哪了，agent 也跳不过校验。这比「靠 agent 记得去读文档」可靠得多。

会话有 **TTL**：agent 开了会话跑一半不提交，超时自动回收。**收尾责任放在 server 侧**——不能要求 agent 显式 close，它一定会忘。

### 5.5 写入路径校验（最关键的一处修订）

原方案最强的一点是：server **从真实文件重切代码、校验证据路径**，因为 LLM 一定会编造。若 agent 写什么就存什么，这一层就没了。

**但这不是矛盾——只是把校验从「生成后」挪到「写入前」：**

```
agent 提议  →  server 验证  →  通过才落库
              ├─ path 必须在真实文件集里存在，否则阻塞
              ├─ 代码从真实文件按行号重切，覆盖 agent 给的
              ├─ 五原理轴完整、段落长度达标、无 N/A/TODO 占位
              └─ 不一致 → 拒绝落库，返回全部问题
```

**这比原设计更好**：验证不再依赖「是谁生成的」，是一个与生产者无关的关卡。**agent 提案、server 验证。**

### 5.6 四个必须定的契约

**(1) 知识单元 = 功能 → 原理 → 卡片**

```
功能（"带退避与截止时间的重试引擎"）
 ├─ 五个原理轴：控制流 / 数据流 / 状态生命周期 / 失败恢复 / 并发时序
 └─ 卡片（可借鉴的最小单位）
      ├─ kind: snippet | skeleton | mechanism | gotcha | decision
      │        （契约给每类「定义 + 正例 + 反例」——只给定义必然跨会话漂移，而漂移会污染聚类）
      ├─ reusable: 是否值得借鉴
      └─ code_spans: [ {path, start_line, end_line, symbol}, … ]   ← 证据，**允许多段**
```

**五个原理轴是关键设计**：强制报告回答「这功能怎么运转」而非「这文件里有什么」；固定轴 = 跨仓报告可比 = 聚类才有意义。

**(2) 报告契约：固定段落，跨仓可比**

固定 4 个段落（VibeCraft 已有此契约，直接沿用）：

```
## Project Characteristics and Signature Implementations
## Executive Principle Summary
## Feature Principle Analysis
## Cross-feature Coupling and System Risks
```

固定形状的意义：**让「Python 的重试」和「TS 的重试」在同一结构下描述，聚类才可能发现它们是同一模式。** 自由格式无法跨仓比较。

**(3) 检索：三通道融合**

| 通道 | 机制 | 补什么 |
|---|---|---|
| vector | 描述向量余弦 | 换词/概念匹配（"退避" ↔ "重试延迟增长"） |
| keyword | FTS5 / BM25 | 精确标识符、错误串、API 名 |
| substr | LIKE | 短查询和中文（分词器救不了） |

用 **RRF（Reciprocal Rank Fusion, k=60）** 融合：`score = Σ 1/(60+rankᵢ)`。RRF 只用排名不用分数，所以余弦距离和 BM25 能投同一张票。效果：**在两路都靠前的 chunk 才胜出**，单路侥幸命中会被压下去。

**融合之后再叠一道 rerank**（cross-encoder，或交给调用方 agent 精排）：RRF 能压掉单路侥幸，但**排不出「哪条真的更可借鉴」**——而这正是本方案最该做对的一步（难点 2）。

**嵌入必须用真语义模型**（多语种 sentence-transformers 或 HTTP embedding 服务）。hash embedder 无语义能力，在它上面「跨语言匹配」这个核心卖点等于不存在，只能当无法安装依赖时的冒烟路径。

**(4) 证据链强制** —— 见 5.5，是整个方案的**可信度基石**。

### 5.7 跨仓聚类：从「习惯」到「模式」

对卡片的**描述向量**做凝聚聚类，**只保留出现在 ≥2 个不同仓库的簇**。

- 一个仓这么做 = 该仓的习惯
- 两个独立仓收敛到同一做法 = **值得借鉴的实现模式**

`min_repos=2` 不是调参，是**语义过滤器**——把「有相似代码」升级成「有通用解法」，这恰是用户要的「看到某几个分析过的项目有类似功能」。

> 召回侧还有一个更深的问题：**用户给的是「意图」，库里存的是「实现描述」**，两者措辞与粒度都不同，直接算余弦会被「表述相似」淹没。技术设计里给出解法（非对称因子分解，作为 V4 的实验分支，用数字决定是否上），见 [`tech-design.md`](tech-design.md) §2.5。

### 5.8 可观测性（agent 驱动下必须补的一环）

一旦分析质量完全归 agent，知识库质量就变成**无界且不可测**。server 必须对每次提交算指标并存库：

| 指标 | 含义 |
|---|---|
| 功能数 / 卡片数 | 覆盖度 |
| 原理轴完整度 | 契约遵守度 |
| 证据覆盖率 | 有多少事实被真实校验过 |
| **`code_mismatch`** | **agent 给的代码 vs 真实切片的差异数** ← 最关键的信任指标 |
| 会话轮数 / 时长 | agent 驱动模式的实际开销（上下文占用与轮数） |

**`code_mismatch` 是唯一的硬门禁：必须为 0，不达标不落库。** 它直接量化「分析者是否在编造代码」，是本方案信任模型的地基——不能当趋势指标看。其余指标（功能数、轴完整度、证据覆盖率、会话 turn/token）先收集分布，再据实定阈。

### 5.9 Web 页面

**做成静态导出而非常驻服务**：`memex export-site` 吐出静态 HTML。**本地形态**下这让它不改动「stdio 进程 + local-first」的形态，不用托管、不用鉴权；**远程形态**下它更省事——把产物扔给同一个反向代理即可，仍然不需要单独跑一个 Web 服务。

**只做「已收录仓库」的目录（catalog），不做卡片浏览器**：一页列出仓库全名 / 语言 / stars / license / 已分析 commit / 功能数与卡片数 / 质量指标 / 是否 stale，外加知识库总览。报告与卡片的具体内容不在此页——需要时直接用 MCP 召回（那才是主入口）。仓库数量天然有限（几十个量级），不设搜索框。

> **远程形态注意**：站点若经反向代理对外，等于把整个知识库的目录页暴露出去。要么放在与 MCP 相同的认证后面，要么只在服务器本机/内网可访问——站点本身不带鉴权（它是静态文件），别让它绕过 §4.4 那道门。

### 5.10 与 VibeCraft 的关系

| 选项 | 评价 |
|---|---|
| **并入 VibeCraft** | ✗ 不建议。Go daemon + React + Python 三进程跑一个 MCP 工具太重；且让「知识库」和「工作台」耦合，用户不装工作台就用不了 |
| **独立项目 + 复用契约** | **✓ 推荐**。沿用 VibeCraft 的报告契约（4 段落 + 5 轴），保证两边报告可比、可互相导入；但代码独立 |

**关键：复用「契约」而不是复用「代码」。** 契约是接口，代码是实施——前者复用收益大且无耦合。

已按这条原则落为可执行路径：`memex import-vibecraft <path>`（`decisions.md` G12、
`tech-design.md` §2.8.2）——**只做结构搬运，且强制过同一套校验**。VibeCraft 的卡片 kind 体系
（3 种 `card_type`）与证据粒度（只有 `path + line`，**无区间、无重切、无 `code_mismatch` 概念**）
都与 memex 契约不同，所以回填必然**只成功一部分**；正因如此才要求「过不了就丢弃并计数」，
而不是把旧数据原样灌进来。

## 六、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **agent 吃光自己的上下文**（新增，最大风险） | 分析仓库把窗口填满，没余量干正事 | 机械活留在 server：静态证据包 + 返回本地克隆路径让 agent 直读；`read_file_slice` 按需取 |
| **agent 漏步骤 / 跳校验** | 半成品入库、无证据的报告 | 服务端会话状态机 + `next_step` 引导 + `commit_report` 强制全量校验 |
| **分析质量不可测** | 库退化成一堆没验证的模型输出 | 每次提交算 `code_mismatch` / 证据覆盖率 / 轴完整度并存库（5.8） |
| **批量分析变苦力活** | 「今晚分析 20 个仓」变成 agent 一轮轮跑 | 保留原 LLM 路径为**可选 batch 模式**，与 agent 驱动共用同一个库、同一套校验 |
| **跨语言匹配不理想** | 召回不到异语言实现 | 对「描述」而非「代码」建向量；接受它需要真模型才有好效果 |
| **向量检索语义能力不足** | 召回不准 | **默认即用真语义模型**（多语种）；hash embedder 仅作无依赖冒烟测试；三通道融合 + rerank 兜底 |
| **切片「行存在但语法残缺」** | 借鉴到残代码 | 校验加深：Python 走 `ast`、其他语言走 tree-sitter，**语法不可解析即拒绝** |
| **agent 不主动查** | 知识库成死数据 | MCP + instructions 显式要求「实现前先查」 |
| **陈旧知识**（仓库变了） | 借鉴到过时实现 | `fetch_repo` 对比远端最新 commit，不一致则标 `stale` 并在召回结果里**显式提示版本**；**不做 git diff 增量**（feature 是逻辑单元，与文件非一一对应，diff 必然漏析），重析是 agent 的自愿动作 |
| **并发写同一仓** | 两个 agent 互相覆盖 | 会话互不干扰；commit 按 `(repo_id, commit_sha, contract_version)` 幂等（G19）——内容一致则 no-op 返回既有 analysis_id，不同则**拒绝并要求显式 `force`**，不静默覆盖 |
| **无生态先例** | agent 驱动的分析质量未知 | V1 单仓闭环先测一个仓（见第七节） |
| **同一仓被重复计入**（改名 / fork / vendored） | 同一个仓的两次分析满足 `min_repos=2`，**模式簇变成自证** | `repos.identity_key` 作真身份锚 + 改名合并（`repo_id` 不变）+ fork 记 `fork_of`；聚类按 `source_group` 计 distinct（G10） |
| **内网 / 无外网 / 私有仓**（新增） | `fetch_repo` 的 clone 与 tarball 两条路全断，服务器也用不上私有凭据 | `MEMEX_GIT_MIRROR` 镜像 + `upload_repo_bundle` 反向投喂（开发机 clone 后上传，server 全程不接触 token）（G22） |
| **远程部署后 agent 读不到克隆目录**（新增） | 「让 agent 用本地 Read/Grep 直读」这条最关键的对策失效，退回 per-file MCP 往返 | `request_repo_bundle`：server 把克隆打成 `git bundle` 单文件下发，agent 拉回本地自读；降级为批量 `read_file_slice`（`tech-design.md` §4.2） |
| **远程服务裸奔**（新增） | 知识库与 clone 能力对全网开放，还可被当跳板 | 强制认证（静态 Bearer Token 起步）+ `Origin` 白名单 + HTTPS + 限流与仓库大小上限（`tech-design.md` §4.4） |

## 七、最终完整形态

**目标形态就是本文档描述的全部内容，一次做到位。** 下面不是「先做简陋版再升级」的降级阶梯，
而是**验证顺序**——每一档都是完整形态的一个验收切面，用来确认前一步的假设成立后才继续堆量。

| 验收档 | 范围 | 通过标准 |
|---|---|---|
| **V1 单仓闭环** | 全部工具就位（17 个），真 agent 分析 1 个真仓库 | 走完 `fetch → evidence → begin → validate → commit → search` 全程，`code_mismatch = 0`；记录 agent 实际 turn / token 消耗 |
| **V2 契约稳定** | 分析 3~5 个中大型、跨语言仓库 | `validate_report` 拒绝率收敛、证据覆盖率达标、五轴无空段 |
| **V3 跨语言** | 若干对「同能力、异语言」实现对照（Python ↔ TS） | **量化跨语言召回 top-k 命中率**，得出「能不能跨语言」的结论 |
| **V4 召回与聚类质量** | 跨仓模式簇成型 | 人工抽检 Top-3 里有多少真可借鉴；模式簇无语言/措辞噪声 |
| **V5 规模** | 增量重析、**改名/fork 去重**（G10）、静态站点、batch 直跑（G21） | 加仓不重析全量；同一实现被 vendored/改名/fork 时**不污染 `min_repos=2`** |

**V1 的判定标准**：不只关心「分析质量」，更要回答**「agent 驱动到底可不可行」**——它要跑多少轮、
会不会把自己的上下文撑爆。只有真 agent 能验证，所以 V1 必须用真 agent，不能离线打桩。

## 八、结论

1. **需求成立且确实空白**：A 环节（读懂仓库）有 4 万★ 方案，你要的 C+D（按意图召回 + agent 自动借鉴）最好的只有 8★。

2. **必须走 B 路线（LLM 深度分析）**：只有它能识别「功能」粒度和判断「可借鉴性」。C 做证据采集，A 做召回层。

3. **B 的执行者应是 agent，不是 server**（本次修订的核心）：
   - 好处：去掉 server 端模型配置、零依赖承诺变彻底、agent 用真实上下文、只跑一个模型
   - 代价：批量分析需保留可选 LLM 路径；分析质量需要专门的可观测性
   - **折中的关键**：**机械工作留在 server（否则吃 agent 上下文），只有生成和判断交给 agent**

4. **三个设计支点不变**：
   - 知识粒度定在**功能级**
   - 对**描述**建向量（而非代码），才可能跨语言
   - **证据链强制校验**，且校验挪到**写入路径**——这比原设计更好，因为验证与「谁生成」无关

5. **流程必须 server 驱动**：会话状态机 + `next_step` 自导向，不能指望 agent 记得步骤。

6. **你的 VibeCraft 已经做完 2/3**：Layer 1（Ingest）和 Layer 2（Search）都在，报告契约也对。缺的只是 **Layer 3（Reuse）+ MCP 暴露**。

7. **建议独立成项目（memex），只复用契约不复用代码。**
